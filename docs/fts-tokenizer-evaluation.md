# FTS トークナイザの評価(trigram / 形態素)

**結論: 現時点では trigram を維持する。**形態素トークナイザ(sqlite-vaporetto)は検索品質と
索引サイズで明確に勝るが、**モデルを SQLite の接続ごとに持つため配信側のメモリが
1 桁増える**。これは「配信機は数百 MB で動く」という chiezo の設計の要を壊す。

2026-07-27 に本番 jawiki から 3 万文書(2.96 億文字)を抜いて実測した。再現は
`scripts/fts_lab.py`(拡張の入手方法もそこに書いてある)。

## なぜ検討したか

FTS5 の trigram は本文を 3 文字の窓に刻んで索引する。辞書が要らず何語でも引ける代わりに:

- **3 文字未満のクエリが原理的に不可能**。`app/fts.py` がタイトル前方一致へ落とすので、
  2 文字の固有名詞(「一蘭」「味仙」)は本文検索できていない
- 「京都」が「東京都」の中の窓に一致するような誤ヒットが出る
- 索引が大きい

## 測ったもの

| | trigram | vaporetto |
|---|---|---|
| 索引サイズ(3 万文書) | 1,383 MB | **381 MB(−72%)** |
| 索引構築 | 130s | **61s** |
| 「一蘭」「味仙」(2 文字) | 0 件(引けない) | **1 位で命中** |
| 「京都」で「東京都」を誤ヒット | する | **しない** |
| 「浅草寺」「夏目漱石」(3 文字以上) | 同等 | 同等(誤ヒットぶん trigram が数件多い) |
| 語の途中からの部分一致(「ンスタントラ」) | **47 件** | 0 件 |
| 英語(`Tokyo` / `tokyo` / `Japan.`) | 引ける | 引ける(ASCII は大小同一視) |
| **接続 1 本の常駐メモリ** | +2 MiB | **+395 MiB** |
| **接続 8 本の常駐メモリ** | +3 MiB | **+926 MiB** |
| **接続 1 本目の初回クエリ** | 0.4 ms | **2,500 ms** |
| 2 回目以降のクエリ | 0.1 ms | 0.1 ms |

## 却下の理由

`api/app/db.py` は**スレッドごとに接続をキャッシュする**。uvicorn の既定スレッドプールは
40 本なので、最悪 40 本ぶんのモデルを抱えることになる(概算 3.5GB)。chiezo は
「取り込みは潤沢メモリのマシン、配信は数百 MB の小型機」という非対称性を設計の要に
置いており(CLAUDE.md「メモリ方針」)、これはその前提を壊す。

初回 2.5 秒も接続ごとに払う。これはモデルの zstd 展開ではなく**構築コスト**で、
非圧縮の `.model`(58MB)を `SQLITE_VAPORETTO_MODEL` で渡しても 2.45 秒までしか下がらない。
クエリのタイムアウトは 5 秒なので、初回だけ半分以上を食う。

## 採用できる条件

1. **モデルをプロセス内で共有できるトークナイザが手に入る**こと。接続ごとに 80〜395MB を
   複製しない実装なら、上の利得(索引 −72%、2 文字クエリ)をそのまま取れる
2. あるいは chiezo 側で **FTS 用の接続を少数に束ねる**(スレッドごとではなく上限つきプール +
   直列化)。クエリ自体は 0.1ms なので直列化しても LAN 用途では詰まらないが、それでも
   モデル 1 本ぶん約 400MB は下限として残る

## lindera を採らなかった理由(別件)

第一候補だった [lindera-sqlite](https://github.com/lindera/lindera-sqlite) 2.0.0 は、
現行の SQLite では**ロード自体に失敗する**。

- `fts5_api` の `iVersion` を 2 と決め打ちしているが、SQLite 3.43 以降は 3 を返す
  (3.46 / 3.53 のいずれでも失敗を確認)
- そこを `>=` に直しても、`SELECT fts5(?1)` で束縛したポインタが NULL のままで、
  FTS5 API を取得できない(crate 側が持つ `sqlite3_api_routines` ミラーの問題と見ている)

lindera は辞書を `.so` に静的リンクして埋め込む(`--features=embed-ipadic` で 19MB)ため、
**接続ごとの複製が起きない可能性がある**。上記が直れば「採用できる条件 1」を満たしうるので、
再評価の価値がある。

## 再現手順

```bash
# 拡張を取る(ビルド不要のバイナリ配布)
curl -sLO https://github.com/hotchpotch/sqlite-vaporetto/releases/download/v0.4.0/\
sqlite-vaporetto-v0.4.0-linux-x86_64-with-model.tar.gz
tar xzf sqlite-vaporetto-*.tar.gz

# 本番 DB から部分コピーを作り、両方の索引を張って比べる
FTS_EXT=./sqlite-vaporetto-*/libsqlite_vaporetto.so \
  python scripts/fts_lab.py build data/jawiki.db lab.db 30000
FTS_EXT=./sqlite-vaporetto-*/libsqlite_vaporetto.so \
  python scripts/fts_lab.py compare lab.db
```

## この評価から実際に入った変更

トークナイザ本体は見送ったが、実験の過程で見つかった問題は別途直してある:

- 検索の並びに人気度を混ぜた(jawiki の `rank_score` が 0.0 固定で死んでいた)
- 並びの第 1 段にタイトル完全一致を置いた(「京都」で記事「京都」が 5 位以内に
  入らなかった)

どちらも「2 文字クエリが引けるようになると数千件ヒットする」という、この実験で見えた
問題への対処で、trigram のままでも効く。
