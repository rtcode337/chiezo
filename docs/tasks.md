# やること(タスク・ルール)

Claude Code に頼みたいことのメモと、守らせたい共通ルールを 1 か所で持つ層。
もとは cc-tasks という別のアプリだったが、**メモを溜めて後から引く**という点で
[notes](api-reference.md#notes唯一書き込めるソースの-rest) と同じことを二重に持って
いたので、こちらへ寄せた。

## 専用のテーブルを持たない

タスクもルールも `notes` の文書 1 件で、**種別・状態・所属はタグで表す**。
おかげでスキーマの変更が 1 つも要らず、**`task` タグを付けたメモが
そのままタスクとして並ぶ**。

| 概念 | 表現 |
|---|---|
| タスク | tag `task` の文書 |
| 状態 未着手 | 状態のタグが無い(既定) |
| 状態 着手中 / 完了 | tag `着手中` / `完了` |
| 「直すのが大変そう」の印 | tag `難所`(状態とは別軸) |
| タスクの所属 | プロジェクト名のタグ(リポジトリ名をそのまま使う既存の慣習に乗る) |
| プロジェクト | tag `project` の文書**1 件**に、全部を JSON でまとめて持つ |
| プロジェクトのアーカイブ | その JSON の `archived` |
| ルール | tag `rule` の文書。本文が Markdown |
| ルールの無効 | tag `無効` |

タグで表せないものだけ `docs.extra`(JSON)に置く —— 並び順(`sort_order`)と、
`docs` が持たない作成日時(`created_at`)。`extra` は `recall` の既定の項目には
入らないので、普通にメモを引く分には見えない。

プロジェクトだけ 1 件にまとめてあるのは、あれが**タスクの入れ物の定義**でしかないためです。
1 プロジェクト 1 メモにしていた頃は、定義が短期記憶に 1 件ずつ並び、並び替えのたびに
メモを書き換えていました。1 件にすると、並びは配列の順そのもので表せます。
JSON を `extra` ではなく本文に置くのは、目に見えないと直せないからです
(`recall` の既定は `extra` を返しません)。**id は JSON の中で採番**し、
消した番号は配り直しません(画面が持っている古い参照が別のものを指さないように)。

所属が**名前のタグ**なのは、プロジェクトを作る前から付いていたタグを後から拾える
ようにするため。`pihole-monitor` タグのメモを先に書いておいて、あとから同名の
プロジェクトを作れば、その時点で紐づく。

## 面をプロセスごと分ける

画面と REST は**同じものが 2 か所から使えます**。使い分けは「外へ出すかどうか」だけです。

| 面 | 入口 | 認証 | 用途 |
|---|---|---|---|
| 本体に埋め込み(`chiezo-app`) | `http://<サーバー>:7010/tasks` | **なし** | LAN 内から使う。管理画面の短期記憶の節にリンクがある |
| 外に出す面(`chiezo-tasks`) | 公開 URL(7015) | Google OAuth | 外から使う。立てるかどうかは任意 |

埋め込み側を素通しにしているのは、**本体がもともと LAN 内・認証なしの面**だからです。
そこには既にメモを消せる口も取り込みを起こせる管理画面もあるので、やること層だけ
認証で守っても増えるものがありません。逆に外へ公開する面は、下の「守り」のとおり
3 つの設定が揃うまで 401 を返し続けます。

**外に出すのは `chiezo-tasks` だけで、知識ベース本体(7010)は LAN 内・認証なしのまま。**
本体を公開すると、次のものが一緒に外へ出てしまう:

| 口 | 公開した場合 |
|---|---|
| `POST /v1/ai/complete` | サーバー側の鍵で AI を叩ける |
| `POST /v1/media/image\|audio\|video\|speech` | 生成が走る。課金に直結 |
| `/admin` | 数時間かかる取り込みを起動できる |
| `DELETE /v1/notes/{doc_id}` | メモを消せる |

認証を 1 枚かぶせて全部を守るより、**外へ出す面と出さない面をプロセスごと分ける**
ほうが、穴が空いたときに失うものが小さい。両者は同じイメージから起動し、
notes の SQLite を共有する(WAL + `busy_timeout` なので別プロセスから書ける)。

## 環境変数(`chiezo-tasks` 側)

| 変数名 | 既定 | 説明 |
|--------|------|------|
| `CHIEZO_NOTES_DIR` | (未設定 = 何も保存できない) | 本体と**同じ場所**を指すこと。ここが実体 |
| `CHIEZO_STATE_DIR` | (未設定 = ログインを保持できない) | セッションと設定の置き場(`tasks_sessions.db`) |
| `GOOGLE_CLIENT_ID` | (未設定 = ログイン無効) | Google OAuth のクライアント ID |
| `GOOGLE_CLIENT_SECRET` | (未設定 = ログイン無効) | 同シークレット |
| `ALLOWED_EMAIL` | (未設定 = ログイン無効) | **ログインを許す Google アカウント 1 件**。ここに一致しない相手は 403 |
| `PUBLIC_BASE_URL` | (未設定) | 公開 URL。リダイレクト URI をここから組む(最優先) |
| `ALLOWED_REDIRECT_HOSTS` | (未設定) | リダイレクト URI の組み立てに使ってよいホスト(ポート込み・カンマ区切り) |
| `LOGIN_RATE_LIMIT_PER_MINUTE` | `20` | ログイン試行の上限(IP あたり) |
| `CHIEZO_TASKS_DEV` | `false` | **認証を通さない開発モード。本番で立ててはいけない** |

**`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `ALLOWED_EMAIL` のどれかが欠けていると、
`/api/**` は 401 を返し続ける。** 設定が無いときに素通しすると、外に出した瞬間に
丸見えになるので、足りないときは閉じる側に倒してある。

Google Cloud Console に登録するリダイレクト URI は
`<公開URL>/login/oauth2/code/google`。

## 守り

- **許可メールは 1 件**。`email_verified` が真であることも確かめる ——
  メールだけで人を同定する設計なので、未検証のアドレスを受け入れると
  「他人のアドレスを名乗るアカウント」で入れてしまう
- **CSRF は二重送信**。`XSRF-TOKEN` Cookie(JS から読める)を `X-XSRF-TOKEN`
  ヘッダで送り返す。ログアウトも免除しない(免除すると外から勝手にログアウトさせられる)
- **PKCE(S256)と `state`** を使う。認可コードを横取りされても交換できない
- **`id_token` を自分で検証しない**。`code` の交換も利用者情報の取得もサーバーから
  サーバーへ TLS で直接行うので、署名を検証する JWT を扱う必要がそもそも無い
- **ヘッダを自分で読まない**。レート制限のキーもリダイレクト URI のホストも
  `request` から取る。`X-Forwarded-For` を自分で読むと、攻撃者が値を変えるだけで
  毎リクエスト別バケットになり制限が丸ごと無効化される。**リバースプロキシの後ろに
  置くときは uvicorn を `--proxy-headers --forwarded-allow-ips=<プロキシのIP>` で
  起動すること**(信頼できる値だけが `request` に入る)
- **リダイレクト URI のホストは許可リストでのみ採用**する(Host ヘッダ注入対策)

## 起動

LAN 内から使うだけなら**何も立てなくて構いません**。本体の `/tasks` が同じ画面を出します。

```bash
# → http://<サーバー>:7010/tasks (管理画面の「短期記憶」節にもリンクがある)
```

外へ公開するときだけ、認証つきの面を別に立てます。

```bash
# .env に GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET / ALLOWED_EMAIL を入れてから
docker compose up -d chiezo-tasks
# → http://localhost:7015
```

**chiezo-app と同じイメージ**で、`command` だけ差し替えて別のアプリを起動している。
画面(Vue の成果物)もそのイメージに焼いてあるので、pull するものは 1 つで済む。

## cc-tasks から移す

もとの cc-tasks からの引っ越しに**スクリプトは要らない**。書き出しと取り込みの
両方を移植してあるので、動いている cc-tasks をブラウザで開くだけで移せる。

| # | cc-tasks 側 | chiezo 側 |
|---|---|---|
| 1 | 「未完了」見出しの **バックアップ** → 書き出し → コピー | やること画面の **バックアップ** → 読み込みに貼る |
| 2 | ルール画面の **まとめて表示** → コピー | ルール画面の **取り込み** に貼る |
| 3 | 規約リポジトリ URL を控える | ルール画面で入れ直す |

**取り込みは冪等**なので、途中でやり直しても増えない((プロジェクト名, タイトル)で
照合して飛ばす)。読み込む前に「作る / 飛ばす」の一覧が出る。

移らないものは次のとおり。書き出しの対象が「戻したいのは待ち行列であって画面の状態
ではない」という考えで決まっているため:

- 完了タスク(書き出しは未完了のみ)
- タスクの並び順、プロジェクトの並び順・アーカイブ状態
- **無効にしてあるルール** —— 「まとめて表示」は有効なものしか出さない。
  必要なら**書き出す前に一時的に有効へ戻し**、移した後に無効に戻す

## 画面(`tasks-frontend/`)

cc-tasks の Vue 3 + Vite + `vite-plugin-pwa` をそのまま持ってきた。**サーバー
レンダリングの管理画面(`app/views/`)とは別系統**で、こちらだけビルドステップを持つ
—— PWA・ドラッグ並び替え・オフラインを HTML 文字列の組み立てに載せ直すのは割に合わない。

```bash
cd tasks-frontend
npm ci
npm run build          # vue-tsc の型検査込み。成果物は dist/

# 開発中(API と画面を別々に上げる)
CHIEZO_NOTES_DIR=./notes CHIEZO_STATE_DIR=./state CHIEZO_TASKS_DEV=true \
  PYTHONPATH=app .venv/bin/python -m uvicorn app.tasks_app:app --port 7015
npm run dev            # :7016 → /api・/oauth2・/login を :7015 へ中継
```

**ポートは 7015**(コンテナの内も外も、本番も開発中の直接起動も同じ)。本体が 7010、
その周辺が 7011〜7014・7019 を使っているので、その次を取っている。開発中のフロントだけ
7016 で、これは Vite の中継サーバーぶん。

- `CHIEZO_TASKS_STATIC_DIR`(既定 `/srv/chiezo/tasks-static`)にビルド成果物を置くと、
  `app/tasks_app.py` がそこから配る。**無ければ 503** で「画面がまだ置かれていません」
- **ハッシュの付いた資材(`/assets/`)だけ長く持たせる**。殻と Service Worker を
  長く持たせると、更新しても古い版が出続ける
- **`/api/` `/oauth2/` `/login/` に前方一致するものは画面に落とさない**。落とすと、
  綴りを間違えた API 呼び出しに殻が 200 で返り、原因を追いにくくなる
- アイコンは `scripts/gen_tasks_icons.py` が書き出す(標準ライブラリのみ)。
  この環境には SVG のラスタライザが無いので、距離関数で描いて zlib で PNG を組んでいる
- **広い画面(64rem 以上)では一覧を段組みにして、画面の幅いっぱいまで使う**。
  段の幅(`column-width`)は下限なので、段は器いっぱいに引き伸ばされる ——
  かつては器を段の整数倍へ丸めて中央に置いていたが、**画面の 2 割前後が使われずに残った**
  (実測 1920px で 1488px)。一覧の 1 行は見出しとボタンなので、長文のように
  行が伸びて読みにくくなるものではない。**入力欄だけは伸ばさない**(`.entry` が上限を持つ)

## そのほかのメモ(`/notes`)

タスク・プロジェクト・ルールの**どれでもない**短期記憶を並べる画面です(決定・環境・
runbook・トラブルシュート…)。短期記憶に溜まる量はこちらのほうが多いのに、これまで
画面から見る手段がありませんでした。

- 新しい順に並び、**タグで絞れます**(候補はこの画面に出るメモに付いたタグだけを数えます
  —— タスクやルールに付いたぶんまで混ざると、押しても 0 件になる候補が並ぶため)
- 一覧は抜粋まで。**全文と生の項目は本体のブラウズ画面**(`/search/notes/doc/{id}`)で見ます
- **読むだけ**です。書くのは MCP の `remember` か本体の `POST /v1/notes` で、ここに足すと
  同じことをする口が 3 つになります

## 1 プロジェクト 1 メモからの移行

プロジェクトを 1 件の JSON メモにまとめたときの移行です。**id は元のメモの doc_id を
引き継ぐ**ので、画面が持っている `projectId` と `/api/projects/{id}` はそのまま通ります。
並びも移行前の順を写します。

```bash
python scripts/migrate_projects_to_one_note.py --notes-dir data/notes          # 下見
python scripts/migrate_projects_to_one_note.py --notes-dir data/notes --apply  # 実行
```

まとめた後は元のメモを消すので、**流す前に置き場をコピーしておくと安心**です
(タスクの所属はタグなので影響を受けませんが、説明とリポジトリ URL は元のメモにしか
ありません)。何度流しても増えません。

## `todo` から `task` への移行

タスクを表すタグは `task` です。以前は `todo` でしたが、あれは「あとでやる」くらいの
意味で普通のメモにも付くので、タスクの基準にするとメモがタスクに化けます。

**移行を流さないと、それまでのタスクが画面から消えます**(基準が `task` タグになるため)。

```bash
python scripts/migrate_todo_to_task.py --notes-dir data/notes          # 下見
python scripts/migrate_todo_to_task.py --notes-dir data/notes --apply  # 実行
```

`--apply` を付けるまで何も書き換えません。書き込むので **chiezo-app と chiezo-tasks は
止めてから**実行してください。何度流しても同じ結果になります(`todo` を持ち、まだ `task` を
持たないものだけが対象)。自動では流しません —— 移行後に付けた `todo`(普通のメモの
つもりのもの)まで巻き込むわけにいかないためです。

## REST(`/api/**`)

パスと本文は cc-tasks のものをそのまま引き継いでいる(移した画面が変更なしで話せる)。
本体の `/v1/...` とは流儀が 2 つ違う:

- **JSON は camelCase**(要求は snake_case でも受ける)
- **エラーは `{"error": {"code", "message"}}`**。画面が `error.message` をそのまま
  表示するので、本体の `{"error": "..."}` に揃えると案内の文言が消える

一覧は `app/tasks_api.py` を参照。
