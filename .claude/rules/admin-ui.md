# 管理画面(app/views/・app/pages.py)

人間向けの HTML を返す画面の組み立てと、管理画面の面・共通の殻。個別の節の詳細はそれぞれの層のルールファイルにある。

## 日時の書式

- `app/jst.py` — **人に見せる日時の書式(JST 固定)**。保存と比較は UTC のまま、
  表示の直前だけここを通す。**変換と書式を 1 か所に集める** —— 画面ごとに書くと
  同じサーバーの中で表記も時差もばらつく。`astimezone()` に任せないのは、
  app コンテナの `TZ` 次第で表示が変わるため(`TZ` はログを読みやすくするためのもので、
  画面の正しさをそこに依存させない)。

## app/views/

- `app/views/` — **人間向けの HTML を返す画面**。`APIRouter` を持ち、`main.py` の末尾で
  `include_router` する。`admin.py`(管理画面と chiezo-trigger へのプロキシ、
  Claude Code 連携設定の配布。`TRIGGER_URL` もここ)/ `browse.py`(`/search/{source}/`)/
  `chat.py`(`/ai/chat` と会話画面の JS)
- **管理画面は面に分かれている**(`PAGES`)。`/admin/status`(状況)/
  `/admin/memory`(記憶。いちばん下が ToDo のルール)/ `/admin/collect`(収集)/
  `/admin/ai`(AI。鍵を預ける面)/ `/admin/media`(AIへの依頼。会話の入口・見比べ・
  作ってもらう口)/ `/admin/server`(その他)で、
  `/admin` はトップ。**1 枚に積み上げない** ——
  見に来る目的が違うものを縦に並べると、いま見たい節に着くまで無関係な表を何度も
  スクロールすることになる。**トップは各面への入口だけ**(概況を 1 行ずつ添えた札)。
  いま動いているもの(ディスクの空き・取り込み・AI への依頼・使用量)は状況の面に置く ——
  トップに並べていた頃は、面を選びに来ただけでも入口が画面の下へ押し出されていた。
  **見出しの「Chiezo 管理画面」がトップへのリンクを兼ねる**(帯に「トップ」は並べない)。
  **使用量は状況の面にも出す**(`_usage_html`)—— 重い仕事を頼む前に見る数字で、
  押す画面から 1 枚めくらせるものではない。**使う相手だけ**に絞って、
  **AI設定の面と同じ表**(`ai_usage.table_html`)を出す。**窓は全部並べる** ——
  いちばん詰まっている 1 つに畳むと**短い窓しか見えない相手が出る**(5 時間が
  詰まっていても週が空いていれば重い仕事は頼めるので、片方では決められない)。
  **描くときに相手へ問い合わせない**(`usage.rows()` は控えを読むだけ)——
  状況の面は何度も開く画面なので、開くたびに外へ出るとレート制限に当たる。
  **取り直したら押した画面へ戻す**(まとめても 1 件ずつでも。`back` と `_back_to`)。
  **どの面にも同じ帯を出す**(`nav_html`。別のモジュールの面からも呼ぶので公開してある ——
  写しを持つと、面が増えたときに片方の帯にだけ出ないことになる)—— トップへ戻ってから
  選び直す、を毎回させない。

## 手元(スマホ)で開いたとき

- **手元(スマホ)で開いたときだけ効く殻**(`app/pages.TOUCH_STYLE` /
  `TOUCH_SCRIPT` / `APP_MANIFEST`)。管理画面は JS を持たない流儀だが、ここは
  見た目の話ではなく**戻る手段が無い**という話 —— ホーム画面から開くと
  ブラウザの帯ごと消えるので、戻るも進むも読み直しもできなくなる。
  - **帯は画面の下に出す**(親指が届くのは下)。**出すのはホーム画面から
    開いたときだけ**(`display-mode: standalone` / `navigator.standalone`)——
    ブラウザで開いているなら、そちらの帯と二重になる
  - **帯は fixed にせず、縦並びの最後に置く。** ホーム画面から開いたときだけ
    body を画面の高さちょうどの縦並びにし、ページ全体はスクロールさせず、
    本文を包んだ `.app-scroll`(`page_shell` が全面に付ける)だけを動かす。帯は
    その後ろに並ぶので、置き直すものがそもそも無い。fixed にして `visualViewport` の
    値で見えている範囲の下端へ JS で置き直していた頃は、**その値そのものが古いまま
    残る経路**(別のアプリでキーボードを出したまま切り替えて来た、など)で帯が画面の
    途中に取り残され、合図や 1 秒ごとの置き直しを足しても塞ぎきれなかった。
    組み替えの印(`html.app-standalone`)は `<head>` の台本(`STANDALONE_HEAD_SCRIPT`)が
    描く前に付ける —— 本文のあとで付けると、ふつうの並びで描いてから組み替わって跳ねる。
    **ブラウザで開いたときは見た目を変えない**(`.app-scroll` はただの箱。body の余白は
    `--page-my` / `--page-mx` で持ち、ホーム画面から開いたときだけ `.app-scroll` の
    内側へ移す)。会話の画面は 100dvh ではなく本文の領域の高さに合わせる
  - **帯のボタンは指で押せる大きさにする**。押せる範囲は帯を 3 等分した全部、
    高さ 52px(48px 以上が目安)、記号の下に小さく名前を添える。**画面の下端
    (ホームインジケーター)のぶんは帯の下に空ける**(`env(safe-area-inset-bottom)`)。
    iPhone はこれを `viewport-fit=cover` が無いと 0 と答えるので、ホーム画面から
    開いたときだけ付け足す(ブラウザで付けると、横向きで本文がノッチの下へ潜る)
  - **引っ張って読み直すのは、いちばん上にいるときだけ**。途中で掴むと、
    下へスクロールしたいだけの指が読み直しになる。**「いちばん上」はページ全体
    だけで見ない**(`atTop`)—— ホーム画面から開いたときはページが動かず
    `window.scrollY` は 0 のままなので、本文の領域と、指の下から外へたどった
    スクロール領域(会話の履歴など)がどれも上端にあるときだけ掴む。**閾値まで引かないと
    何も起きない**(触れただけで読み直すと書きかけの入力が消える)。
    入力の中では掴まない(選択やカーソル移動を邪魔する)
  - **Service Worker は持たない。** やること画面を畳んだときに外したもので、
    スコープがルート直下を掴み、殻を抱え込んで**更新しても古い版が出続ける**。
    ここで欲しいのは「帯を消して開く」ことだけで、オフラインで動かしたい
    わけではない —— マニフェストだけ置く
  - **外の部品は読まない**(LAN 内・オフラインで動く前提)。JS が動かなければ
    何も起きないだけで、画面はそのまま使える

## app/pages.py と管理画面のエンドポイント

- `app/pages.py` — 管理画面・ブラウズ画面共通の HTML 組み立てヘルパー(`page_shell`, `esc`)と、
  画面の URL(`browse_url` / `doc_url`。出典のリンクもここを通すので、移すときに漏れない)。
  **URL を HTML に埋めるときも `esc()` を通すこと** — `browse_url` の中の
  `urllib.parse.quote` は percent-encode であって HTML のエスケープではない
  (CodeQL に反射型 XSS として指摘された。`tests/test_api.py::TestUrlLayout` が固定)。
  ファビコンは `assets/icon.svg` を最小化した data URI(`FAVICON_DATA_URI`)として埋め込む
  (app イメージのビルドコンテキストは `app/` のみで `assets/` を含まないため。原本を変えたら更新)。
  iPhone の「ホーム画面に追加」用に 180×180 の PNG(`APPLE_TOUCH_ICON_PNG`)も持ち、
  `page_shell` が `<link rel="apple-touch-icon">` を出す + `main.py` が
  `/apple-touch-icon.png` で配信する — iOS は SVG や data URI のファビコンをホームアイコンに
  使わないため。角丸マスクは iOS が自前で掛けるので角丸なし・全面塗りで描いてある
  (再生成手順は docs/development.md「アイコンを変えたとき」が正)。
  共通スタイル(`PAGE_STYLE`)は狭い画面向けにメディアクエリを 2 つ持つ。
  `56rem` 以下は**表だけ**を `display: block` + `overflow-x: auto` で横スクロールさせる ——
  列の多い表(登録ソース一覧は約 800px 要る)が画面からあふれると、ページ全体が横スクロール
  して本文まで画面外へ出るため。表を `<div>` で包む必要がないので、画面ごとの HTML 組み立ては
  触らずに済む。本文の抜粋(`td.snippet`)だけは折り返す(1 行に伸ばすと表が果てしなく広くなる)。
  `40rem` 以下(スマホ)は余白を詰め、ボタンと入力欄を指で押せる大きさにし、
  **表を 1 行 1 枚の札に起こす**(`table.as-cards`)。横スクロールに逃がすだけでは
  列の多い表が読めない —— **どの列を見ているかを覚えていないと値の意味が取れない**
  ので、7 列ある表(巡回の一覧)では指を往復させ続けることになる。
  見出しは `thead` を隠して各値の脇へ回し(`data-label`)、値の左に小さく置く
  (上に積むと 1 行が 2 行になり、札が縦に伸びて結局スクロールが増える)。
- **列の名前は、出来上がった HTML に 1 回だけ配る**(`pages.as_cards`。
  `page_shell` が呼ぶ)。**表は画面ごとに手で組んである**(31 か所)ので、
  1 つずつ `data-label` を書き写すと書き漏らしと食い違いが必ず出る。
  足すのは**属性だけ**で中身は 1 文字も動かさないので、表の切れ目を読み違えても
  最悪「名前が付かない欄がある」で済む(壊れた HTML にはならない。
  `tests/test_mobile_shell.py` が本物の面で往復を押さえる)。
  見送る表が 2 つある: **見出しの無い表**(`thead` を隠すと名前の付かない値が
  並ぶだけになる)と、**またがる見出しを持つ表**(`<th colspan="6">` は列の名前
  ではなく表そのものの札で、配ると 1 列目だけに見当違いの名前が付く ——
  **間違った名前を付けるほうが、名前が無いより読めない**)。
  **台本の中は触らない** —— 会話の画面は表を JavaScript の文字列として持っていて
  (`app/views/chat.py`)、そこを書き換えると台本そのものが壊れる。
  掛かりは本番でいちばん大きい面(2.4 MiB・24,674 欄)で実測 49 ms、
  ふつうの面(60 KB)で 0.35 ms
- `/`(GET) — `/admin` へ 302 リダイレクト
- **見出しは 3 つの面に畳んである**(`知識(溜めて引く)` / `AI(貸し出すもの)` /
  `このサーバー`)。冒頭の建付けと同じ切り口で並べるため —— 画面と文書で節の切り方が
  違うと、片方を読んだ人がもう片方で迷う。
  焼き先が長期記憶(`corpus/`)そのものなので、位置と実態が一致している。行に出るのは
  **長期記憶の件数**。**「今すぐ実行」と「ドライラン」は巡回ごとに置く** ——
  相手も 1 回に見る量も巡回ごとに違うので、収集に 1 つだけ置くと
  「どの設定で走ったのか」が押した本人にも読めない。集めるのも焼くのも
  取り込みの中で起きるので、集めると焼くを分ける段は無い
- **外の絵(サムネイル)を取れているかを状況の面の「画像」の節に出す**(`_images_section_html`。AI の節の下。
  ディスクの空きの下に並べていた頃は、取り込み・収集・AI の節より前に絵の話が割り込んでいた。
  `_thumbs_health_html` / `thumbs.health`)。続けて 3 回取れなければ
  ⚠️ で目立たせ、相手と理由(「HTTP 429」)を添える。**断られて休んでいる間は、1 回目でも期限を出す**
  (出さないと「最後に取れた時刻」が止まっている理由が読めない)。
  **「いま走っている依頼」には、CLI ブリッジの相手なら手順・道具・最後の動きと後ろの待ちを添える**
  (`_bridge_progress_html` / `answer.bridge_progress`。走っている依頼のある相手のブリッジにだけ聞く。
  最後の動きから 5 分を超えたら ⚠️)。
  **画像の節には、その下に絵の依頼の控えを畳んで出す**(`_thumbs_log_html` / `thumbs.recent_log`。直近 200 件、
  誰の頼みか・どの絵か・取った/写しを返した/作れない/取れない/休み中)。1 行の具合だけでは、
  頼みが届いているのか、届いて何が返っているのかが読めなかった。一時的な失敗は 1 件ごとの印に残らないので、Wikimedia に断られ
  続けてもどの面にも出ていなかった
- **データの置き場のディスクの空きを管理画面に出す**(`_disk_html`)。
  **コンテナの中から見える** —— `/data` は bind マウントなのでホストの実体の統計が返り、
  ホストの `df` と一致する(実測で確認)。出す理由は**この画面から始まる操作が
  ディスクを一番食う**から(取り込み 1 回で数十 GB。jawiki の DB は 42GB)。
  足りないまま走らせると数時間かけて最後に失敗するので、押す前に見えるところに置く。
  単位は GiB(`df -h` と同じ数え方。GB で書くと df の表示と食い違って見える)
- `/admin`・`/admin/osm`・`/admin/wikipedia`(GET) — 簡易 HTML 管理画面(画面に何が出るかは
  `docs/api-reference.md`「人間向けの画面」節が正)。
  **画面は知識の 2 層をそのまま節に分ける**: 長期記憶(`mutable` でないソース =
  取り込みで焼く読み取り専用のもの。素材は外のダンプか、AI に集めさせたもの)と
  短期記憶(`app/notes.py`。書き込める置き場)。
  **1 つの表に混ぜない** —— 混ぜていた頃は notes の行にも再構築ボタンが出ていて、
  押すと trigger が `unknown source` を返すだけなのに、確認ダイアログだけが
  「ダンプの取得からやり直します」と言っていた(**書き込めるソースで、
  消えたと読める文言がいちばん危ない行に出ていた**)。件数の出どころも違い、
  長期は走査時の値、短期は描画時に数える(`notes.count()`)。
  短期の節は**中身そのものを出さず、件数とタグの分布まで**にする ——
  1 件ずつ読むのはブラウズ画面の仕事で、そちらは見に行った人だけが見る。
  **見せ方は長期側と同じ表**(見出しのすぐ下)。見に来る人が知りたいことは
  どちらの節でも同じ(何件あって、最後に動いたのはいつで、いまの形で引けるか)なので、
  片方だけ文にすると見比べるときに目の動かし方が変わる。
  **ただし列は写しにしない** —— ダンプも取り込みも無いので `dump_date` と `built_at` は
  書きようがなく、空欄が並ぶだけ。代わりに**最後に書かれた時刻**を出す
  (`notes.last_updated()`。短期記憶で「動いているか」を言えるのはそこ)。
  `lang` も持たない。検索への入口は表の中(名前と操作の欄)に置くので、
  節の下に別のリンクを並べない。
  **並びは短期記憶 → 長期記憶**(書く場所が先、溜まる場所が後)。
  **設定の置き場(`app/machine_store.py`)はその間に、別の節として出す**
  (`_machine_html` / `/admin/memory#chiezo-settings`)—— **ソース名は
  `chiezo_settings`**(`state/chiezo_settings.db`)。ソース名は jawiki や収集と
  同じ平たい名前空間に並ぶので、`settings` のような一般の語だと、外のアプリが
  同じ名前で収集を頼んだときにぶつかる(短期記憶を `chiezo_memory` にしたのと同じ判断)。
  **改名の移行は、配り終えたので外してある** —— 入れ替えた直後だけ必要なもので、
  残すと「いつ外すのか」が誰にも分からなくなる。
  中身は設定であって覚えたことではないので
  短期記憶の表には混ぜないが、**分けた結果まったく見えなくなっていた**。
  収集が消えた・戻ってきたのような話を追うとき、まず確かめたいのは「設定がどこに、
  いつの姿で残っているか」。**目録だけ出して中身は 1 件ずつ開く**(区画の台帳を
  抱えた 1 件は数百 KB になり、面を開くたびに運ぶことになる)。
  **直す口は置かない** —— ここを手で書き換えても、次に機械が書いた拍子に消える。
  **長期記憶の表の下に「Wikipedia の画像(Kiwix のオフライン版)」の節**(`_wiki_zim_section_html`)。
  置いてある版(置いていなければそう言う)・Kiwix の一番新しい版と「最新版を落とす」(`_zim_offer_html` →
  `POST /admin/zim/download` → trigger の `POST /zim/run`。もう最新版がある・空きが足りない・ダンプの枠が
  埋まっているときは押せず理由を添える)・定期の取り直し(`_schedule_form`。予定は `rebuilds` に `wiki_zim.JOB` の名前で持ち、
  `main._tick_rebuilds` が `trigger_zim_run` で起こす)。**データを持ち込む操作は記憶の面** —— 状況の面に
  置いていた頃は、いま動いているものを見る面にデータを作るボタンが混ざっていた。
  **「未初期化データの初期化」は長期記憶の節の中へ畳む**(h3 +
  `<details id="init">`)—— あれを開くのは新しいソースを入れるときだけで、
  日々見に来るのは長期記憶の一覧と「集める」のほう。同じ高さで並べると、
  見たい節に着くまで使わない表を何度もまたぐことになる。
  **取り込みを起こすボタンは `run_buttons_disabled()` の 1 か所で押せるかを決める**:
  chiezo-trigger が未設定・到達不能・実行中のどれかなら押せない。**あれは長期記憶へ
  書き込むときだけの相手で、立てない構成が普通にある**(compose も `depends_on` に
  書いていない)。押せてしまうと 502 が返るだけで理由が画面から読めないので、
  代わりに「読むだけならこのままで動きます」と状態欄に出す。**そのぶん
  「未初期化データの初期化」からは `kind=memory` を外す** —— 両方に出すと
  どちらを押せばいいのか読めない。
  実装側の要点は 3 つ: **取り込み中でも自動リロードしない**(`page_shell` は
  `<meta http-equiv="refresh">` を持たない)—— 5 秒ごとに読み直していた頃は、
  開いた `<details>` が閉じ、書きかけの入力が消え、押そうとしたボタンが読み直しに
  攫われた。取り込みは数時間かかるので、その間ずっと画面が使えないことになる。
  **見たい人がブラウザで読み直す**(状態欄に読み直しの入口は置かない。
  再読み込みと同じことしかできず、1 行を食うだけだった) / `osm_<国>` 195 件と `<lang>wiki` 348 件は
  そのまま並べると他のソースが埋もれるので `group` で 1 行に畳み、国・言語の選択だけを
  `/admin/osm`(大陸ごとの `<details>`)・`/admin/wikipedia`(`WIKIPEDIA_TIERS` の記事数階層ごと)
  へ切り出す / `?q=` の絞り込みは JS なしのサーバ側フィルタ。
  **末尾に「いま動いているビルド」を出す**(`app/build_info.py`)—— タグ(`latest`)は
  上書きされ、デプロイ先が pull し忘れても外からは見えないので、イメージ自身に
  素性を持たせる。値は CI が `--build-arg` で焼き込み(`CHIEZO_BUILD_SHA` /
  `CHIEZO_BUILD_TIME`)、**渡らなければ「不明」と出すだけでビルドは通す**
  (手元ビルドを壊さない)。Python には Go の `runtime/debug.ReadBuildInfo` に
  当たる仕組みが無いので、自動では入らない。表示は JST 固定(オフセットで持ち、
  tzdata を引かない)。
  **3 つのイメージを並べて出す**(`_builds_html`)—— app・取り込み・CLI ブリッジは
  別々に焼かれるので、**片方だけ古いまま**が普通に起きる(直したはずの不具合を
  追いかけ続けることになる)。取り込みは `GET /status` の `build`、ブリッジは
  `GET /health` の `build` / `built_at` から読む —— **ブリッジは LAN に口を
  開けない**ので、版を外から確かめる手段がここしかない。**立っていないものは
  出さない**(聞きに行くのはこの面だけ。版を確かめに来る面で、開く頻度も低い)。
  **書式は 1 つに揃える**(`describe_of`)—— 並べて見比べる面なので、
  同じ意味の行が違う顔で出ては用をなさない
- `/admin/init/{source}`(POST) — `chiezo-trigger` の `POST /run/{source}` へプロキシし、
  `/admin/status#job` へ 303 リダイレクト(進み具合は状況の面で見る)。`CHIEZO_TRIGGER_URL` 未設定なら 503、未知ソースなら 404、
  登録済みソースなら 409
- `/admin/rebuild/{source}`(POST) — 登録済みソースの再構築(init と同じプロキシで、
  要求条件だけ逆: **登録済みであることを要求**し、未登録は 404。未登録の取り込みは init 側)。
  ソースの正は trigger 側の `ADAPTERS` なので、カタログに無い登録済みソースでも trigger に
  判断を委ねる。**例外は短期記憶(`Source.mutable`)で、ここで 409 にする** ——
  取り込みで焼くソースではないので trigger も断るが、そこまで行かせると
  「実行しようとして失敗した」に見える。管理画面は「最新のスキーマバージョン」(`latest_schema_version()` —
  trigger の `GET /sources` が返す `schema_version` = ingest の `core.SCHEMA_VERSION`。
  取れなければ app の `max(SUPPORTED_SCHEMA_VERSIONS)` で代替)を表示し、
  それより古い DB の行に注意書きを付けて再構築を促す(app が読めるのは最新だけなので、
  これが出るのは取り込み側が先に版を上げたとき)
