# 収集の道具(フィード・Pi-hole・サムネイル・リンク確認・手で回す巡回)

巡回に付く機械の道具と、外を読む道具。手元の長期記憶から引く `extract` は `collect-extract.md`。

## 巡回に付く道具

- **配信元ごとに順番に取る**(`feeds._fair_share`)。まとめてから新しい順に
  切ると、**更新の遅い配信元が永久に入らない** —— 速い配信元が上限を埋めてしまう
  (1 日 60 件超の配信元と数日おきの配信元が同居していて、後者が 0 件だった)
- **JSON の API も読める**(`feeds._json_mapping` / `_json_entries`)。1 本ごとに
  どの項目が見出し・URL・要約・日付かを書く(ドットでたどるか `{…}` に埋め込む)。
  **RSS / Atom の 1 件と同じ形に写す**ので、後ろの工程は区別しない。話題の論文
  (Hugging Face の Daily Papers)が JSON の API しか配っておらず、RSS だけを読む
  道具では入れようがなかった
- **Pi-hole から引く巡回もある**(`Sweep.use_pihole` / `app/pihole.py`)。LAN の
  Pi-hole の問い合わせの記録を AI を呼ばずに読み、**止めたドメインと気になる通信を
  ドメインごとの集計として積み上げる**(最初と最後に見た時刻・回数・アクセス元ごとの
  回数)。**前の回の脇書きに足した値を返し**、焼くときは運んだ鍵で入れ替える
  (`collect.carries_facts`)。**どこから読むかは文書の `last_seen` が覚えている**
  (ドメインごとにそれより後の行だけ足すので、カーソルを持たない)。
  **毎回作り直す長期記憶のソースにしなかったのはこのため** —— 写しでは積み上げられない。
  **新しく溜めるのは止めたものと気になる通信だけ**(普通の通信まで溜めると、
  調べる回に家庭の数千のドメインが並ぶ)。タグは最初の 1 回しか付かないので、
  いまの状態は脇書きで読む。接続先とパスワードは API キーの面の `pihole_url` と
  `pihole_password`(**別々の欄** —— 1 つの欄だった頃は URL を直すだけでパスワードを
  打ち直すことになった。取り込みのソースではないので、
  `views.admin._TOOL_KEYS` で面に並べ、URL の欄は `secret: False` で隠さない)。
  **いま止めている通信をその場で読む口もある**(`GET /v1/pihole/blocked` /
  `pihole.blocked_since`)。溜めずに Pi-hole を読むだけで、**セッションは閉じずに
  使い回す**(5 秒おきに読まれるので、毎回ログインすると Pi-hole の控えが埋まる)
- **隣の区画にあるものを見せられる**(`{nearby}` / `collect.render_nearby`。矩形で割る
  収集だけ)。区画を 200m 広げた範囲にある、区画の外の 1 件を見出しと座標で並べる。
  **`{current}` は区画の中しか見せない**ので、密集した地区では境目の向こうに既にある
  店を、漏れを足す回が足し直していた
- **まだ焼いていない固定の数を返す**(`collect.pending_locks` /
  `GET /v1/collect/{name}` の `locks_pending`)。固定の記録(`locks`)は反映したあとも
  残る(AI に座標を動かさせないため)ので、読む側が記録の数で「いま反映する」の口を
  出すと、反映が済んでも消えない(実際にそうなった)。長期記憶の座標と固定を突き合わせ、
  違うものだけを数える。**比べるのは座標と固定の印だけ**(タグの並びは AI が書き直すと
  変わる)。全件は読まず、固定した見出しだけを引く
- **人が座標を固定した 1 件は、AI の墓標だけでは消さないようにできる**
  (`Collection.locked_doubt_tag` / `collect._doubted`)。書いておくと、固定を持つ 1 件への
  墓標を「そのタグを足して残す」に置き換え、理由は脇書きの `doubt_reason` に置く。
  **頼むだけでは守れない**(座標の固定と同じ理由)—— 依頼文で「消さないで」と書いても、
  別の回の AI が閉店と読めば消える
- **RSS 1.0(RDF)も読む**(`feeds._items`)。あの形は `<item>` が `<channel>` の
  外に並ぶので、RSS 2.0 のつもりで channel の下だけを見ていると**丸ごと 0 件**に
  なる(いちばん件数の多い配信元がそうなっていた)
- **検索文を AI に考えさせてから引ける**(`app/search_queries.py` /
  URL の `{query}` / 巡回の依頼文の `{queries}`)。検索の RSS は、**同じ検索文で
  引き直しても同じ記事が返るだけ** —— 固定の検索文の収集では、1 回目に 158 件
  入ったあと 2 回目は全部が既にあるもので弾かれた。**機械で引く巡回の依頼文に
  `{queries}` を書いた回だけ**が考える(`thinks`。巡回の依頼文は空なら収集のものに
  倒れるので、「依頼文があるか」では見分けられない)。考えるのは `_harvest` の中
  (`main._search_queries`)で、**相手はその巡回の相手・ワーカー**。
  **1 回目は最初の組(`feed.queries`)を使い、AI は呼ばない**。**最近使った検索文は
  使わず、使えるものが出なければ 409** —— 最近の検索文のまま引いても何も増えない。
  **ただし二度と使えない形にはしない**(`reuse_days`、既定 60 日)—— 記事は増えて
  いくので、しばらく経てば同じ切り口で新しい記事が当たる。使い直した回の件数は
  **その回で増えたぶんだけ**(タグは回をまたいで同じなので、前の回までに数えたぶんを引く)。
  **件数は 2 つ数える**(入った数と、消されずに残った数)—— 入った数だけ見せると、
  宣伝や的外れを大量に連れてくる検索文が当たりに見える(本文検索は語を含む記事を
  ゆるく拾うので、実際に大半が外される回があった)。**展開したあとの本数も
  `MAX_URLS` に収める**(`per_run` を切る)。**控えは Chiezo が持つ**
  (`queries/<名前>`)—— 呼ぶ側に持たせていた頃は、Chiezo で収集を作り直しても
  前の収集の検索文が残り、新しい収集ではまだ走っていない検索文が「0 件」と数えられて
  最初の組が走らないまま置き換わった。**収集を消せば控えも消える**。
  **下見(ドライラン)では考えさせない**(焼かない回で控えに積むと、本番の回が
  「使ったことがある」として弾く)。控えは管理画面の収集の面で見られ、消せる
  (`_queries_html`)。**`{queries}` を持つ巡回があるのに `{query}` が無ければ
  保存で 400**(走るまで分からないと、考えた検索文がどこにも使われない)
- **1 件ごとの絵も運ぶ**(`feeds._image` → `extra.image`)。読むのは
  **フィードが配っているものだけ**(`media:thumbnail` / `enclosure` /
  `hatena:imageurl`)—— ページを取りに行くのは本文を取ることになるのでしない
- **読む側のアプリから頼まれて縮小版を作る口もある**(`POST /v1/thumbs`。`main.make_thumb`)。
  アプリが Wikimedia の写真を自分で取りに行っていた(外への通信先が散らばる)ので、Chiezo が取り次ぐ。
  中身は下の `thumbs.make` と同じ(同じ絵は 1 度だけ・置き場の写しを返す)。**取りに行けるホストは
  `main.THUMB_HOSTS`(いまは `upload.wikimedia.org`)だけ** —— 読む側から URL を受け取って外へ出る口なので、
  何でも通すと外を叩かせる踏み台になる。**はてなの件数も同じ考えで取り次ぐ**(`GET /v1/bookmarks` /
  `app/bookmarks.py`。50 本ずつ・間を空け・1 時間覚える。引けなかった URL は返さない)
- **サムネイルを持てる**(`Collection.thumbs` / `app/thumbs.py` / `GET /v1/thumbs/{name}`)。
  読む側の画面が `extra.image` をそのまま指すと、**開くたびに見る人のブラウザが
  知らない外のサイトへつなぎに行く**ので、焼く前に 1 回だけ取って縮め(長辺 320px の
  WebP)、`extra.thumb` として Chiezo から配る。**作るのは AI が返した絵だけ** ——
  配信が運んだ絵は配信元が自分で配っているもので、読む側がそのまま指せばよい
  (`from_feed`)。**配信に絵を載せない相手だけ、名指ししたホストのページの
  `og:image` を拾う**(`pages_from`)—— 上の「ページを取りに行かない」の例外で、
  名指しした相手の頭 512 KB だけを読む(`"*"` はどのホストも —— 1 件が公式サイトを
  指す作品・イベントの収集向け。配信が絵を運んだ 1 件は読まない)。**1 件 1 回**(作れなければ `thumb_failed`。
  一時的な失敗 —— つながらない・5xx・429 —— には付けない。前に 429 で付けた印は `RETRYABLE_FAILURES` で取り直す)で、
  印は脇書きなので焼き直しても残る。Wikimedia の元の絵は縮小版(`wikimedia_thumb`)を先に取る。
  取れたか・断られたかは `thumbs.health`(設定の置き場のフラグ `thumbs_health`)に控え、状況の面と `GET /v1/thumbs/health` で読む。
  1 枚ごとの結果は `thumbs.recent_log`(フラグ `thumbs_log`。直近 200 件。`make` の `caller` が誰の頼みか)に残し、状況の面に畳んで出す。
  429 を言われたらその相手へは `RESTING_SECONDS`(30 分。Retry-After が長ければそちら)頼まず(`Resting`。外へ出ずに断る)、
  収集の中で取っている回は残りをやめる。Wikimedia は作り置きの無い縮小版を作らせる頼みを回線ごとに数えて絞る。
  **Wikipedia のオフライン版(Kiwix の ZIM。`app/wiki_zim.py`・`CHIEZO_ZIM_DIR`)にある絵は外へ出ずに引く**(`thumbs._make` が外より先に聞く)。
  断られて休むたびに埋まるのが止まり、写真が何日も埋まらなかったため。**置いていれば、そこに無い Wikimedia の絵も
  取りに行かずに諦める**(`thumbs.NotOffline`。外の絵の置き場には覚えない —— 新しい版を置けばその場で引ける)。
  置いていなければ今までどおり取りに行く。解凍せずに 1 件ずつ読み、置き換えはファイルの一覧と更新時刻で気づいて開き直す。
  ZIM の中の名前は `_assets_/<md5("https://upload.wikimedia.org/wikipedia/<プロジェクト>/")>/<URL の名前を decodeURI した形>`
  (作り手の mwoffliner の決まり。予約された文字 `,` `&` `?` は符号のまま。`asset_names`)。控えの結果は「オフライン版から取った」、
  置いているかは記憶の面(`_wiki_zim_section_html`)と `GET /v1/thumbs/health` の `offline`。
  落とすのは chiezo-trigger(記憶の面の「最新版を落とす」と定期の取り直し。`ingest/zim_download.py`)。
  **確かめた結果は外の絵の URL ごとに覚える**(`app/image_memory.py`・短期記憶の置き場 `chiezo_images`。
  見出しは URL の sha1、タグは `取れた` / `無かった` と `ホスト:<相手>`)。**無かった絵は `RECHECK_DAYS`(30 日)
  経つまで外へ出ずに `Skip` する**(`thumbs._make`)—— 覚えていなかった頃は、無い本の表紙を読む側のアプリが
  画面を開くたびに聞き直し、本番と手元の 2 つのアプリが同じ絵を何度も聞いた。表紙・写真・収集のサムネイルの
  どれでも同じ。一時的な失敗(つながらない・5xx・429)は `Skip` にならないので覚えない
  **URL は AI や外のページから来る**ので、名前を引いて手元・LAN のアドレスを断り、
  転送も 1 段ずつ確かめる(`app/outbound.py`。フィードと URL で渡された元も同じ関門を通る)。**置き場は状態ディレクトリ** ——
  生成物の置き場(`/media`)は日が経つと掃除されるので使えない。
  1 回に作るのは `MAX_PER_RUN` 件まで(配信の回は毎時走るので、溜まりも数回で片付く)。
  **足すだけの回は、返ってこなかった既にある 1 件にも後から作る**(`thumbs.backfill` /
  `collect.waiting_for_thumbs`)—— 見出しと脇書きだけの 1 件を足し、足すだけの回の
  「脇書きしか受け取らない」で中身を動かさずに載せる
- **1 件の URL を確かめられる**(`Collection.links` / `app/link_checks.py` /
  `GET /v1/collect/{name}/links`)。AI が口コミサイトの店の番号を推し量って書いた URL は
  別の店の頁になり、地図辞典の公式サイト欄にはドメインごと無くなったものが残る ——
  読む側がそのまま人に見せると、押しても開かないリンクが並ぶ。**事実だけを控え、
  使うかは読む側が決める**(状態・転送先・頁の題名。題名が名前と合うべきかはサイトに
  よるので、決まりを Chiezo に持たせない)。**文書には書かず `state/links.db` に URL で
  控える** —— 脇書きに載せるには焼き直しが要り、名簿の回が週に 1 度の収集では結果が
  届かない。時計(`main._run_link_checks`)が 1 分ごとに 20 件ずつ開く。
  **断られた(401/403/429)は開けないとは数えない**(人のブラウザでは開ける)。
  一時的な失敗は 3 回続くまで「分からない」のまま。**モジュール名が `links` でないのは、
  `main.py` に出リンクの口 `links()` があるから**(import 名がぶつかる)
- **巡回の設定は、その行の下に畳んで置く**(`_sweep_edit_row` /
  `POST /admin/collect/{name}/sweep`)。**1 本ずつ保存する** —— 収集ぜんたいの
  編集フォームに全部を並べていた頃は、1 本の間隔を直すのに他の巡回まで送り直して
  いた(別のセッションが同時に別の巡回を直していると、後から押したほうで上書き
  される)。**見ている行の真下に置く**のは、離れていると「どの行のものか」を
  名前で照合することになるため。名前を書けば増え、消せば減るのは変えていない
- **機械で引く巡回に相手は選ばせない**(画面にも出さないし、保存時にも落とす)。
  選んでも何も起きない —— 機械の回は AI を呼ばずに返すので、相手もモデルも
  読まれない。**選べるのに効かない欄は「設定したつもり」を作る**。
  控えに残すのも避ける(後から読む人には「この回は AI で走っている」と見える)
- **手で回す巡回を置ける**(`Sweep.by_hand`・`app/handoff.py`)。**web の画面から
  使う AI に頼む道** —— 鍵も API も持たない代わりに調べものが速い相手がいる
  (Gemini の web 版)。Chiezo からは呼べないので、**依頼文をファイルにして
  人が渡し、答えのファイルを読み込む**。
  **両端はいつもと同じ部品を使う** —— 依頼文は `collect.build_messages` が
  そのまま組み、答えは `collect.parse_response` がそのまま読む。だから焼く道も
  墓標も URL の重複も未精査の印外しも区画の印も、AI に頼んだ回と同じところを
  通る(**真ん中だけが人**)。
  **束には「何をして、どの形で返すか」を材料より先に書く**
  (`collect.handoff_body`)—— 材料だけ渡すと、web の画面は要約や感想を返す。
  **区画ごとに節を分ける** —— まとめて 1 つの依頼文にしていた頃は、範囲が
  「(全体)」になり(`build_messages` は区画を 1 つしか取らない)、しかも
  差し込みが天井(`MAX_MATERIAL_DOCS`)で切られた。本番の 1 束目は
  5 区画・497 件のうち 300 件しか載らず、**主な仕事である「この範囲に
  足りない店を足す」が 1 件も返ってこなかった**(タグの手入れだけが返った)。
  節に分ければ、どの節も「その範囲の全部が並んでいる」を保てる。
  **添える一言も画面に出す**(`handoff.PASTE_NOTE`)—— ファイルを添付する
  だけでは読んで作業してもらえない。
  **預かれる束は 1 つ** —— 溜めると、どの束の答えなのかが分からなくなる。
  **印を付けるのは束に入れて渡した区画だけ**(焼くときに選び直さない。
  答えが返るまでに台帳は動きうるので、渡した範囲と印を付ける範囲がずれる)。
  **時計では走らない**(`is_due`)—— 走らせる中身が揃うのは読み込んだときで、
  予定で起こすと空振りする。**ワーカーにも任せない**
  (`normalize_sweeps` が `worker` を落とし、積む段
  (`main._fill_worker_queues`)と行列の掃除(`_no_longer_due`)でも弾く)——
  時計を止めただけでは足りなかった: **ワーカーを選んだままの巡回を
  手で回す回へ変えたら、待ち行列がそれを毎周流し続けた**
  (答えが無いので 409 で落ち、そのたびに取り込みが 1 本無駄になる)。**次の束は答えが焼けたら組む**
  (`main._refill_handoffs`。区画を回る収集だけ。そうでない収集は押したとき ——
  あちらは「いまの外の様子」を聞く回なので、聞きたいときに作るのが自然)。
  **中身はファイル、目録は設定の置き場** —— 束は区画 5 つで 200 KB になるので、
  収集の定義と同じ行に混ぜない(あちらは 1 つ読むたびに全部を運ぶ)
- **外の道具で引く巡回も置ける**(`Sweep.use_feed`)。フィードが配っている
  見出し・要約・URL・配信日を、AI を呼ばずにそのまま溜める回。**取りこぼしも
  宣伝記事も引き受ける代わりに、枠を使わずに毎時回せる** —— 重要度を付ける・
  まとめる・漏れを探す、といった判断の要る仕事は別の巡回が AI に頼む
  (名簿と肉付けを分けるのと同じ形)。**区画は見ない**(機械で引く回と同じ理由)。
  **進み具合にも触らない** —— 次にどこから読むかは道具の側が決める
  (`feeds.SINCE_LAST_RUN`)。出典ごとにタグを書けるので、ニュースと記事と論文が
  同じところに溜まっても、後から分けて取り出せる。
  **「前回より後」の基準はその巡回の前回**(`main._harvest`。`{recent}` と
  同じ読み方)—— 収集の前回を基準にすると、**別の巡回が走った時刻でその窓が
  食われる**。1 時間おきに溜める回でも、直前に整理が走っていれば見るのは
  数分ぶんだけで、あいだに配信されたものはどの回も溜めないまま流れていく
  (整理の側でも噛み合わない —— 4 時間ごとに回るのに、差し込まれる見出しは
  直前の回からのぶんしかない)

## 外向きの道具(app/feeds.py)

- **外向きの道具**(`app/feeds.py` / 定義の `feed` / プロンプトの `{feed}`)。
  `extract` が手元から機械的に引く道具なら、こちらは外から引く道具 —— 狙いは同じで
  **AI が間違えるところと、間違えないところを分ける**(見出し・URL・日付は機械が
  正確に取れる。何が重要でどう束ねるかは取れない)。
  - **使い道は 2 つ。** ①`{feed}` へ**参考として**差し込む(何を溜めるかは AI が
    決める。自分でも web を検索し、渡されたぶんも含めて採否を判断する。差し込む文にも
    そう書く)。②**機械的にそのまま溜める**(巡回の `use_feed`)。
    **どちらを使うかは巡回が決める** —— ①は「フィードが拾わなかったものも入る」
    代わりに AI の枠を使い、②は「拾った宣伝記事もそのまま入る」代わりに枠を使わずに
    毎時回せる。溜めていく一方の収集では②で集めて、判断の要る仕事だけを別の巡回で
    ①や `{recent}` に頼む形になる
  - **配信元が 1 件ごとに付けている語も読む**(`<category>` / `<dc:subject>` /
    Atom の `term` 属性。`_subjects`)。**書き手が付けた語は、AI が推し量った
    分野より確か** —— 読まずに捨てていた頃は製品名がタグに一度も現れず、
    そこから作るトピックの網も「AI」「セキュリティ」のような広い語ばかりになった。
    `{feed}` の行に `[語: …]` として出す。**文書のタグには混ぜない** ——
    束の名前と出典は「後から出典ごとに外す」ための印で、そこに記事ごとの語が
    混ざると外す鍵として使えなくなる
  - **手元のネットワークを指す URL は取りに行かない**(`app/outbound.py`。サムネイルと共通)。
    定義は外のアプリからも置けるので、LAN の機器を叩かせる踏み台にしない。転送は自動で
    追わず 1 段ずつ確かめ、読むのは `MAX_BYTES` まで。LAN の相手(Pi-hole)は専用の道具が持つ
  - **外へ出る作法は `app/websearch.py` と同じ契約**。本文は取りに行かない
    (見出し・要約・URL・日付だけ)、自分でレート制限をかける、`User-Agent` は
    プロジェクト名だけ。**無人で回る層なので、加減しないと相手のログに
    等間隔の足跡だけが延々と残る**
  - **DOCTYPE のある XML は読まない**(`_looks_unsafe`)。実体参照の展開で
    メモリを食い尽くす細工への門前払いで、フィードに DTD が付くことは実際まず無い
  - **1 本落ちても収集は止めない**(参考の素材なので、1 本の不調で止めるほうが損)。
    **取れなかった数は素材の中で伝える** —— 少ないのが世の中の都合か道具の不調かで
    意味が違う
  - **日付を持たないものは `since` で落とさない**(そういうフィードは普通にあり、
    絞ると静かに 0 件になる)
  - **外の URL を叩けるのは有効にした収集だけ。** 定義は誰でも置けるが、走り出すのは
    管理画面で有効にしたときだけなので、そこが唯一の関門になる
