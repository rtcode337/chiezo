# 使用量・失敗の控え・依頼の履歴

各 AI の使用量(枠と Chiezo が使ったぶん)、失敗の控え、依頼の履歴の画面。

## app/usage.py / app/usage_store.py

- `app/usage.py` / `app/usage_store.py` — **各 AI の使用量**(`/v1/ai/usage`・管理画面の
  「使用量」節)。**数を 2 つ持ち、混ぜない**:
  - **相手が言う枠**(`quota`)…… 相手の勘定なので**残りが分かる**が、**聞ける相手が限られる**。
    聞き方は `Provider.usage`(`app/providers.py`)で相手ごとに決まる ——
    **CLI ブリッジの 3 つ(claude / codex / antigravity)はブリッジの `/usage`**
    (CLI に聞かせる。**手元に控えた認証情報は期限切れになる**ので、更新は CLI に任せる)、
    **手元に控えた認証情報は期限切れになる**ので、更新は CLI に任せる)、
    openrouter は `/api/v1/key`。

    **claude はかつて「枠を出せない相手」だった。** Chiezo が
    `app.anthropic.com/api/oauth/usage` を直に叩いていて、**あの口は `user:profile` を
    要求する**のに、預かっているのは `claude setup-token` の長期トークン
    (安全のため推論だけに絞られている)—— 実測で HTTP 403
    `OAuth token does not meet scope requirement user:profile` だった。
    **口が無いのではなく、叩く口を間違えていた** —— `claude -p "/usage"` で取れる
    (実測。print モードのスラッシュコマンドで、会話を始めずに CLI 自身の報告が
    `result` に入って返る)。**「取れない」と書いてある理由は、疑ってから消すこと。**
    **出せるのはコンテナの中でサインインしたときだけ** —— 登録できる
    `claude setup-token` の長期トークンは推論だけに絞られていて、`/usage` は
    締めの集計を返す(`Total cost: $0.0000` / `num_turns` も 0。当時「出せない」と
    判断したのはこの文面で、そこは今も変わっていない)。**登録が空のときだけ
    CLI 自身のサインイン結果に任せる**(`apply_credential`。antigravity と同じ形)
    —— 登録があるとそちらを環境変数で置くので、登録したままサインインしても
    枠は出ない。**`/srv/bridge/home` を名前付きボリュームにしておくこと**
    (無いとコンテナを作り直すたびにサインインが消える)。
    **締めの集計が返ったら、打つ手を添えて返す**(`_looks_like_a_wrap_up`)——
    0 が並んだ集計をそのまま見せても、壊れているのか頼み方が違うのか読めない。**戻る時刻に年が書かれていない**ので、ブリッジが
    いちばん近い将来として ISO に直す(`_claude_reset_at`。`(UTC)` と
    書かれているときだけ直し、別の呼び方には手を出さない)。

    openrouter は `/api/v1/key`。**gemini・openai・推論サーバには口が無い**
    (前者は Google Cloud の Quotas API 側、後者は Admin キーが要る)ので
    画面には「この相手は枠を出さない」と書く —— **空欄にすると「使っていない」と読める**
  - **Chiezo が使ったぶん**(`spent`)…… `data/state/usage.db` に 1 呼び出し 1 行で残し、
    5 時間 / 24 時間 / 7 日で集計する。**全部の相手で同じ物差し**だが、
    **Chiezo を通していない利用は入らない**(手元の端末で回した CLI など)。
    記録するのは `answer.complete_message`(会話)と `media._run` / `media.transcribe`
    (絵・音・動画・声)—— **絵と音も同じサブスクの枠を食う**ので同じ表に入れる
  決めごと:
  - **どの聞き方もモデルを呼ばない**(「接続を試す」と同じ方針。確かめるたびに枠を食わない)
  - **画面は描画のときに聞きに行かない。** 控えと取得時刻を出し、取り直しは行のボタン。
    API も既定は控えを返し、`?refresh=1` のときだけ外へ出る ——
    **見ているだけで相手のレート制限に当たらない**ため
  - **取れなかったときに前の値を消さない**(一時的に繋がらないだけのことがある)。
    値と失敗の理由を並べて出す
  - **窓は短い順に並べる**(`usage.ordered`)。相手ごとに返す順が違う
    (実測: codex は 5 時間が先、antigravity は週が先)。詰まりやすいのは短いほうなので、
    受け取る側で揃える。**長さの分からない窓は末尾に、元の並びのまま**
    (claude は文面から読むので長さを持たない)
  - **聞けた値は推移としても積む**(`quota_samples`)。控え(`quota`)は「いまどうか」で
    上書きされるので、**無人で回る層が枠を食っても、跳ねた時刻も 1 ポイントぶんの
    重さも後から読めなかった** —— 2 点無いと差が取れない。**相手 × 窓ごとに分ける**
    (相手は枠を何本も持つ。混ぜると別々に減る枠が 1 本の線に潰れる)。
    **上がったぶんだけを足す**(`quota_trail`)—— 窓は転がって明けるので、下がった差は
    「戻った」であって「使わなかった」ではない。
    **窓の名前はぶつかりうる**(実測: codex は長さの違う 2 つの窓をどちらも
    `primary` と名乗る)。名前は線を束ねる鍵なので、ブリッジ側で窓の長さを使って
    呼び分ける(`_unique_ids`)—— ぶつかったままだと**別々の窓が 1 本の線に混ざり**、
    使用率が交互に跳ね上がったり 0 に戻ったりして見える。
    **ぶつかったものは全部付け替える** —— 片方に元の名前を残すと、どちらが残るかが
    相手の並べ方次第になり、次に聞いたときに入れ替わる
  - **枠の呼び名は窓ではなく束のほうに書いてある**(`limitName`)。ブリッジが
    親から持って降り(`_collect` の `group`)、Chiezo が見出しへ添える
    (`直近 7 日(gpt-reserve)`)—— **窓の長さもぶつかる**ので、長さだけでは
    読み分けられない(実測で、codex は 7 日の窓を 2 つ返し、どちらも
    `primary` / `secondary` としか名乗らなかった)。**id は名前として使わない**
    —— あれは機械の鍵で、読む人に意味が伝わらない
  - **相手が言ったそのままも控える**(`Quota.raw` / 画面の「相手が言ったそのまま」)。
    **窓に直せたときも控える** —— 画面に出るのは Chiezo が付けた名前と割合だけで、
    窓の名前すら相手のものではない(ぶつかれば長さを添えて呼び分ける)。
    **元を当たる道が無いと「この行は何なのか」に答えられない** ——
    実測で、codex が返す 2 つ目の `primary` が何の制限なのか画面から読めなかった。
    **整形も翻訳もしない**(そのまま検索できることに値打ちがある)。
    **取れなかった回は前の控えを消さない**(窓と同じ扱い)
  - **同じ名前の窓は id を添えて呼び分ける**(`usage.arranged`)。名前は長さから
    作るので、同じ長さの窓が 2 つあると見分けが付かない(実測: codex は 7 日の窓を
    2 つ返す。別勘定で値も違う)。**ぶつかったものは全部添える** ——
    片方だけ素のままにすると、どちらが素かが相手の並べ方次第になる
  - **相手が返さなくなった窓は下へ回す**(`quota_trail` の `stale`)。名前が変われば
    その線はそこで止まる。**消さずに印を付けて末尾へ** —— 消すと後から確かめ
    ようがなくなるが、生きている線と同じ顔で並ぶと読み違える。
    **混ざっていた頃の線は「上がったぶん」を大きく持つ**ので、直したあとも
    一番上に居座る(実際にそう見えた)
  - **観測点ごとに、そのあいだの依頼も出す**(`calls_between`)。使用率だけでは
    「跳ねた」までしか分からず、どれを止めればよいかが決まらない。
    **区間は前の観測の直後から今の観測まで** —— 始まりを含めると、観測の
    ちょうどその秒に入ったぶんを隣り合う 2 つの区間が二度数える
  - **定時に聞きに行く**(`main._sample_quotas`。`CHIEZO_QUOTA_SAMPLE_MINUTES`、既定 15 分)。
    押したときだけ聞く作りでは点が溜まらない。**前の点より後に 1 度も呼んでいない
    相手には行かない**(`calls_since`)—— 前と同じ値が返るだけで CLI を 1 本起こす
    ぶんだけ損をする。**1 点目だけは呼ばれていなくても採る**(起点が無いと差が取れない)。
    **窓が戻った相手も採る**(`usage.needs_resample`)。あわせて**ワーカーの判断では、
    戻る時刻を過ぎた窓を 0 として読む**(`usage.busiest` / `has_reset`)—— 詰まって
    避けられた相手は呼ばれず、呼ばれないので取り直されず、窓が明けても古い値で
    避けられ続けていた
    **番は印 1 つで取り合う**(`claim_quota_poll`)—— `--workers 2` なので同じ周期で
    両方が起きる。**境界は「より古い」で見る**(`<`)。時刻は秒までしか持たないので、
    「以下」で通すと同じ秒の 2 つが両方とも番を取る
  - **トークン数の `NULL` は「相手が言わなかった」、`0` は「使わなかった」。**
    混ぜると、数を返さない相手(CLI ブリッジ)が「0 トークンで動く相手」に見える
  - **`settings.db` に相乗りしない** —— あちらは消してはいけない設定の置き場で、呼ぶたびに
    書く表を同居させたくない(ジョブ DB と同じ判断)
- **失敗の控え(`app/ai_log.py`)には生成の失敗も入れる**(`kind` 列)。
  job にも `error` は書いてあるが、あれは頼んだ本人が `image_status` で引くための
  もので置き場の掃除で消える。**後から「何が落ちたか」を見に来る人**は job_id を
  知らないので、会話の失敗と同じ表に並べる(記録するのは `media._note_failure`)
  - **推測で数字を作らない。** ブリッジは読めた形だけを窓にして返し、読めなければ
    CLI の返事をそのまま渡す(画面はそれを理由として出す)

## 依頼の履歴と使用量の画面

- `app/views/ai_history.py` — 管理画面の状況の面の「依頼の履歴」(中身だけ。見出しと畳みは呼ぶ側)。**成功と失敗を分けない**
  —— 失敗だけを見ていた頃は「落ちていないのに結果が変」「そもそも呼べていたのか」が
  読めなかった。同じ 1 本の流れなので同じ表に並べ、**結果の欄で見分ける**
  (失敗だけ見たいときは絞り込み)。**会話と生成も分けない** —— どちらで落ちたか
  分かっていない人が探せなくなるので、種類は列で示す。
  **素材は 2 か所にある**(成功は `usage_store`、失敗は `ai_log`)。**片方に寄せない**
  —— 失敗を集計側に混ぜると「使ったぶん」が水増しになり、成功を失敗の控えに混ぜると
  500 件の枠がすぐ埋まる。**並べるときだけ突き合わせる**のが、どちらの意味も壊さない。
  **ページングを入れてある**(既定 10 件)—— 無人で回る層(収集の時計)ができたので
  依頼は放っておいても増え、全部出すといちばん見たい直近が埋もれる。
  状態は JS を持たないのでクエリで運ぶ(`?ai_page=` / `?ai_failed=1`)。
  **状態の 0 は「届かず」と書く** —— 数字の 0 だけだと成功に読める。
  **相手の欄にはモデルと考える量の両方を出す**(`who_html`)—— 考える量はモデルと
  同じくらい結果と時間を左右するので、「同じ相手・同じモデルなのに片方だけ遅い」の
  理由がここに出ていないと読めない。そのために `usage_store` にも `effort` を
  足してある(失敗の控えには元からあり、成功した行だけ持っていなかった)。
  **畳んだ回の考える量は、送ったモデルの名前から取り出す**
  (`answer._effort_of` / `providers.effort_in_model`)—— 畳んで送る相手
  (`folds_effort` = claude / codex)では 2 つ組を送らないので `cfg.effort` が空で、
  返ってくるのは相手が解決した素の名前(`claude-fable-5-1`)。**走っている間だけ
  見えて、終わると消えていた**(`/v1/ai/inflight` は送る値をそのまま出すため)。
  Antigravity だけ残っていたのは、あちらの slug に元から段が入っているから。
  **段の一覧は控えも見る**(`answer._EFFORTS_CACHE`)—— codex の段は CLI 側の
  控えにしか無く(`providers.get("codex").efforts` は空)、定義だけで読むと
  いちばん段を選び分ける相手の行が空欄のまま残る。
  **トークンの `None` は「相手が言わなかった」、`0` は「使わなかった」**(混ぜると、
  数を返さない CLI ブリッジが「0 トークンで動く相手」に見える)
- `app/views/ai_usage.py` — 管理画面の「使用量」節と「取り直す」の受け口。
  **窓ごとに消費ペースを添える**(`usage.pace_of` / `_pace_html`)—— 使った割合を窓のうち
  経った割合で割って、戻るまで足りるかを出す。使った割合だけでは、窓の始めの 40% と
  終わり際の 40% の区別が付かない。**取った時点で数える**(いまの時刻で割ると甘く出る)。
  窓の 1 割が経つまでは見積もらない。長さを持たない窓は名前から読み(`window_length`)、
  読めなければ出さない
  **「AI の相手」の表とは分けてある** —— あちらは設定を一度入れたら開かない場所、
  こちらは何度も見に来る場所(重い仕事を頼む前に枠を見る)。
  **内訳の下に枠の推移も出す**(`trail_html`)—— どの依頼が走っていたかと、
  枠がいつ動いたかは、並べて初めて突き合わせられる。観測点は畳んで出し、
  **前回からの差を添える**(使用率だけ並べても、跳ねた場所は引き算しながら読むことになる)。
  **表の下に内訳を出す**(`breakdown_html`。相手 × モデル × 考える量 × 依頼元で束ね、
  多い順に `BREAKDOWN_ROWS` 組まで)。**相手ごとの合計だけでは、詰まった枠の中身が
  読めない** —— 同じ相手に無人で回る層の巡回と外のアプリの依頼が混ざって入るので、
  使い切ったと分かっても次にどれを止めればよいかが決まらない。
  **回数の隣に目方(`usage_store.breakdown` の `prompt_bytes` / `reply_bytes`)も出す**
  —— CLI を包んだ相手はトークン数を言わないので、回数だけでは 20 KB の依頼と
  300 KB の依頼が同じ 1 回に見える。窓は `?spent_window=` で切り替え、既定は 24 時間
  (**5 時間では無人で回る層の一周が入らず、7 日では今日の跳ね上がりが均される**)。
  **知らない窓は既定へ倒す**(`breakdown_window`。`_back_to` と同じく、照合して
  通すのではなくこちらが持っているほうを返す)。**状況の面には出さない**(あちらは概況)。

## 控えと目方の表

- **控えと目方は 1 つの表に出す**(`views/ai_history.py`)。**紐は
  `transcript_id`**(`usage_store` / `ai_log` が持つ)—— 別の表に分けていた頃は
  同じ 1 回が 2 か所に並び、突き合わせる手がかりが時刻と相手しか無かった
  (同じ秒に 2 本走っていると、どちらの中身か決められない)。**控えが無い行は
  目方だけになる** —— 残る長さが別(目方 30 日 / 失敗 500 件 / 控え 14 日)なので、
  中身だけ先に消えた行は普通に出る。**目方は控えの中に重ねて出さない** ——
  控えの側は役割の名札を付けて綴じた文字列を測るので、同じ 1 回に違う数が 2 つ並ぶ

## /v1/ai/failures

- `/v1/ai/failures`(GET) — **AI への問い合わせが失敗したときの控え**(新しい順)。
  無人の呼び出しのために置いてある。定期実行が朝に落ちても、呼んだ側のログに残るのは
  `llm error 502` の一行だけで、**その場に居合わせないと理由が消える**
  (実測: 外のアプリの朝の提案が `claude failed` だけを残して落ちた)。
  記録するのは相手・モデル・状態・理由と**プロンプトのバイト数**まで。
  成功のほうは `usage.db` に**やり取りの目方**(依頼文と応答の大きさ・かかった時間)を
  残す —— トークン数を言わない相手では、これが「何をした呼び出しか」の唯一の手がかりになる。
  **中身は残さない** —— プロンプトと応答には呼んだ側の材料がそのまま入る
  (保有銘柄、家庭内の通信先…)。大きさだけ残すのは、失敗が大きさに寄っているのかを
  後から見分けるため(実測では寄っていなかった: 307KB が落ちた 90 分後に 324KB が通っている)。
  置き場は `state/ai_failures.db`(`app/ai_log.py`)。**`settings.db` とは別のファイル** ——
  あちらは消してはいけない設定、こちらは消してよい観測。`MAX_ROWS` で頭打ちにする

## /v1/ai/usage

- `/v1/ai/usage`(GET) — **各 AI の使用量**(枠の残りと、Chiezo が使ったぶん)。
  **既定では相手へ問い合わせない**(控えを返す)—— 画面もダッシュボードも定期的に引く口で、
  引かれるたびに外へ出ると見ているだけでレート制限に当たる。取り直すのは `?refresh=1`、
  1 相手だけなら `?backend=`。**CLI が動いている相手は飛ばす**(`usage.busy_now`。
  枠を聞くのは CLI をもう 1 本起こす動作で、走っている最中は空くまで待たされて
  時間切れになる)。飛ばしたぶんは応答の `skipped` に出る。
  中身の決めごとは上の `app/usage.py` が正
