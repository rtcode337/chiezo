# 短期記憶(notes・名前付きの置き場)と ToDo

書き込めるソース `chiezo_memory` と名前付きの置き場(`/v1/stores`)、その上に載る ToDo(タスク・プロジェクト・ルール)。

## app/notes.py

- `app/notes.py` — **「覚える」層(`/v1/chiezo_memory`)の本体。人と AI が書き込む場所**(名前付きの置き場も同じモジュール)。
  **ソース名は `chiezo_memory`**(モジュール名は `notes.py` のまま。改名したのは
  名前空間に並ぶほうで、`machine_store.py` が `chiezo_settings` を持つのと同じ形)。
  **`notes` や `memory` のような一般の語にしない** —— ソース名は jawiki や収集と
  同じ平たい名前空間に並び、外のアプリが `POST /v1/collect` で同じ名前を要求できる。
  `memory` を選ばなかったのは、固化の層が焼いていたソース名がそれで、古い控えや
  ログと history 上で混ざるため。
  **改名の移行と古い名前の橋渡しは、配り終えたので外した**(`chiezo_settings` の
  改名でも同じように後で外した)。
  環境変数 `CHIEZO_NOTES_DIR` はそのまま —— あれは「書き込めるソースの置き場」で、
  ソース名とは別の軸(設定の置き場の改名でも `CHIEZO_STATE_DIR` は触っていない)。
  使い方は `docs/api-reference.md`「chiezo_memory(短期記憶)の REST」節、
  なぜこの形かは `docs/design-notes.md`
  「「覚える」(notes)はなぜ Chiezo に置くのか」が正。実装側の要点:
  - **`CHIEZO_NOTES_DIR` が機能フラグを兼ねる**(未設定 = 503、MCP の道具も出さない)。
    ツール定義は常時コンテキストに載るので、使えないものを並べない
  - **タグの定番語彙は `CANONICAL_TAGS` の 1 か所で持ち、MCP の `remember` の
    ツール定義(`tag_guide()`)として配る**。クライアント側の CLAUDE.md に写しを
    持たせると写しごとにずれる(実際に NAS と nas に割れた)。語彙を変えるのは
    この定数だけでよい —— テストが「語彙がツール定義に載ること」を突き合わせる
  - **タスク・ルールはタグで表す**(`task` / `着手中` / `完了` / `難所` / `rule` /
    `無効` / `project` / `アーカイブ`。所属プロジェクトはリポジトリ名のタグ)。
    **専用のテーブルも列も足さない** —— 種別も状態も絞り込みの軸でしかないので、
    `doc_tags` の索引がそのまま効く。状態のタグが無いものが「未着手」で、
    これなら一番多い状態にタグを増やさずに済む
  - **タグで表せないものだけ `docs.extra`(JSON)に置く**。いまは並び順
    (`sort_order`)だけ。**`recall` の既定の項目には入れない** —— 入れると
    `extra` を持たないほとんどのメモにも `"extra": null` が並び、`recall` を読む
    AI のコンテキストを食う(`RECALL_OPTIONAL_FIELDS`。要る側が `fields` で名指しする)
  - **`Body(...)` を既定値に持つ引数を増やしたら、MCP 側で明示的に渡すこと**。
    `app/mcp_server.py` は FastAPI を通さず `app/main.py` のハンドラを直接呼ぶので、
    省略すると `FieldInfo` オブジェクトがそのまま保存側へ流れる
    (`tests/test_notes.py` の `test_mcp_remember_still_works_without_extra` が押さえる)
  - **置き場を取り込み本体(`/data/corpus`)と分けるのは性能上の理由**。
    `registry.data_dir_fingerprint()` が `CHIEZO_DATA_DIR/*.db` の mtime/size を 5 秒ごとに
    見て、変われば**全ソース再走査(`COUNT(*)` 込み)**する。同じ場所に置くとメモ 1 件ごとに
    jawiki 150 万件の COUNT が走る。**バインドするホストのディレクトリは `data/` 1 本**で、
    その下を `corpus/`(本体)・`notes/`(覚える層)・`state/`(管理画面の設定)に切っている ——
    走査するのは `corpus/` だけなので、1 本にまとめても再走査は起きない
  - **読み手は `mode=ro`**(`db.set_mutable_paths` / `registry.Source.mutable`)。
    `immutable=1` は「開いている間このファイルは変わらない」という宣言で、SQLite は
    ロックも WAL 確認もしない。追記される DB をこれで開くと壊れたページを掴む
  - **`docs_fts` は external content 方式なので自動同期しない**。ingest が全件投入後に
    `INSERT INTO docs_fts(rowid, title, body) SELECT …` しているのと同じことを 1 件ずつやる。
    削除は `INSERT INTO docs_fts(docs_fts, rowid, title, body) VALUES ('delete', …)` が要る
    (入れたときと同じ値を渡さないと索引に残る)
  - **DDL は `ingest/core.py` の写し**(app は ingest を import しない)。ずれると
    「notes だけ filter が 409」のように静かに壊れるので、`tests/test_notes.py` が
    ingest 側から作った DB と `sqlite_master` を突き合わせて落とす
  - **名前付きの置き場を外のアプリが作れる**(`notes.create_store` / `POST /v1/stores` /
    `/v1/stores/{name}/…`)。**中身の形も口の形も短期記憶と同じ**で、関数は `store=` で
    置き場を名指しする(既定は `chiezo_memory`)。アプリの記録や設定を短期記憶に相乗り
    させると、AI が `recall` したときにアプリの JSON が混ざって出るので分ける。
    **置き場は `CHIEZO_NOTES_DIR` に `<名前>.db` で並ぶ** —— `scan_all` がこのディレクトリを
    丸ごと走査するので、作った時点でソースとして登録される。**作ってから使う**
    (作っていない名前への書き込みは 404。書いた拍子に作ると、打ち間違いが黙って
    新しい置き場を生む)。**同じ名前は 409**(作り直しの口にしない —— 2 つのアプリが
    同じ名前を選んだとき、後から来た側が前の中身に書き足すのを防ぐ)。名前は収集と
    同じ規則で、既にあるソース・収集の名前は断り、収集の側も置き場の名前を断る。
    **中身のある置き場は消せない**(`registry.blocked_from_deleting` が `notes.is_store` を見る)。
    **空の置き場だけ、記憶の面の表から消せる**(`notes.delete_store` / `POST /admin/stores/{name}/delete`。
    使わなくなった置き場が一覧に残り続けると、どれが生きているのか読めなくなる)。件数を数えるのと
    ファイルを消すのは書き込みのロック(`BEGIN IMMEDIATE`)を取ったまま行う。API には出さない。
    管理画面の記憶の面の表には、短期記憶・設定の置き場と並べて名前付きの置き場も出す
    (出さないと、アプリが何をどこに預けているか画面から見えない)。会話の口(`/v1/talk`)の
    キャラ設定も、置き場を名指しすれば(`store`)そこから読む
  - **置き場は収集の書き込み先にもなる**(`Collection.store`。`collect.md`「置き場へ書く収集」)。
    書くのは必ず `notes.add` を通す(FTS とタグの索引がずれないように)。**収集は足すだけで、
    置き場の中身を書き換えも消しもしない** —— アプリが直接書いたものと同じ場所に並ぶため
  - **本体は複数のプロセス(`--workers 2`)で動くので、置き場を作ったプロセス以外にも気づかせる。**
    作ったプロセスだけがその場でソースに足すので、ほかのプロセスは `immutable=1` で開いて
    開いた時点の中身を読み続けていた(書いたメモが 0 件に見える)。読み書きの入口(`notes.ensure_db`)が
    `db.mark_mutable` で自分の DB を名指しし、再走査の指紋(`main._sources_fingerprint`)には
    置き場の名前だけを足す(大きさや時刻まで見ると、メモ 1 件ごとに全ソースを走査し直す)
  - **件数は読む側が数え直す**(`notes.count()` / `refresh_count()`)。`doc_count` は
    走査時の値で、notes は指紋に入らないので走査のきっかけが起きない。かつては
    書いた側で直していたが、**書き手は画面だけではない** —— MCP の `remember` も
    取り込みも同じ DB へ書くので追いつかない(実際に件数が 12 のまま
    実体 42 になっていた)。短期記憶は数十〜数千件なので、読むたびに数えても
    長期側の 150 万件を数え直すのとは費用がまるで違う
  - **想起の主役は全文検索ではなく時系列の見込み**。「さっき話したあの件」は語が
    一致しないため、`recall` は `q` を省いて `updated_at` 順に引ける形にしてある
    (`idx_docs_updated` は notes だけが持つ。コアスキーマの追加ではないので
    `schema_version` は上げない)
  - **`limit`/`offset` の上限は `notes.recall()` の中で担保する**。REST の
    `Query(ge=1, le=…)` は HTTP の口にしか効かず、MCP と agent は app の関数を
    Python から直接呼ぶので通らない。SQLite は **`LIMIT -1` を「無制限」と解釈する**ため、
    素通しすると頁を送る意図の呼び出しが静かに全件取得になる。`max_chars` の負値も
    同じ理由でここで 0 に丸める(Python の負の添字は末尾を削る意味になる)
  - **本文は既定で 400 文字に切る**(`RECALL_MAX_CHARS_DEFAULT`)。絞り込めても
    1 件あたりが重いままだと、20 件当たれば 20 件分の全文がコンテキストに載る。
    他ソースの `search`(冒頭)→ `doc`(全文)と同じ二段構えにするための既定で、
    `max_chars=0` で切らない。`fields` で項目も選べる(`RECALL_FIELDS`)
  - **切ったものには `truncated: true` を立てる**。黙って切ると「これで全部」と
    読まれる —— 504 を 0 件と読むのと同じ取りこぼし方をするため、全文が要ると
    分かる印を必ず返す(取り直し先は `/v1/chiezo_memory/doc/{doc_id}`)

## app/tasks.py

- `app/tasks.py` — **ToDo の層(タスク・プロジェクト・ルール)。画面は
  `app/views/todo.py`(記憶の面の「プロジェクトとタスク」「ルール」の節)**。
  **notes の上にタグで載っているだけ。専用のテーブルも列も持たない**。
  種別も状態も所属も絞り込みの軸でしかないので `doc_tags` がそのまま効き、
  おかげで移植にスキーマ変更が 1 つも要らなかった。実装側の要点:
  - **`task` タグを付けたメモが、そのままタスクとして並ぶ**。専用のテーブルを
    持たない作りの要。**`todo` とは分けてある** —— あちらは「あとでやる」くらいの
    意味で普通のメモにも付くので、タスクの基準にするとメモがタスクに化ける
  - **状態のタグが無いものが「未着手」**。一番多い状態にタグを増やさずに済み、
    既存のメモに手を入れなくてよくなる
  - **プロジェクトは設定の置き場の 1 件に、全部を JSON でまとめて持つ**
    (`app/machine_store.py`。`project/definitions`)。**覚えたことではなく設定** ——
    タスクの入れ物の定義でしかないのに短期記憶に置いていたので、**人が消せてしまう**
    (消すと全タスクの所属が消える)し、目的の違うものが `recall` や検索に混ざっていた。
    収集の定義やワーカーと同じ扱いにしてある。
    **1 件にまとめる**のは、1 プロジェクト 1 件だった頃に並び替えのたびに全部を
    書き換えていたため —— まとめると**並びは配列の順そのもの**で表せる。
    **id は JSON の中で採番し、`next_id` を持ち回る** —— `max(id)+1` だと最後の
    1 件を消した後に番号を配り直し、画面が持つ古い参照が別のものを指す。
    **中身が壊れていたら黙って作り直さない**(中身ごと消えるので 400 で見せる)
  - **タスクの所属は「実在する `project` の名前と一致するタグ」**。
    プロジェクトを作る前から付いていたタグが、その名前の `project` を作った瞬間に
    紐づく。名前を変えたら `_rename_project_tag()` が全タスクのタグを付け替える
  - **プロジェクト名に構造タグ・定番タグは使えない**。名前はそのままタスクに付く
    タグになるので、`完了` のような語だと「所属」ではなく「状態」と読まれてしまう
  - **書き込みは必ず `app/notes.py` を通す**。`docs` を直接 UPDATE すると FTS と
    `doc_tags` / `tag_counts` が本体とずれる。例外は `notes.set_extra()` だけで、
    `extra` は索引のどれにも関わらないから直接書いてよい
  - **並び替えで `updated_at` を動かさない**(だから `set_extra()` が要る)。
    カードを 1 枚ドラッグしただけでメモが `recall` の先頭に浮くと時系列が乱れる
  - **ルールだけは本文にタイトル行を混ぜない**。`combined()` が `## <見出し>` を
    自分で付けるので、混ぜると見出しが二重になる(タスクとプロジェクトは逆に、
    notes が空本文を許さないので本文をタイトルから始める)
  - **連結(`combined()`)と取り込み(`parse_rule_markdown()`)は対**。前置きと
    「規約リポジトリの扱い」は連結時に自動で付くので取り込みでは捨てる ——
    捨てないと貼り替えのたびに増える。捨てる見出しは `COMBINED_REPO_RULE` の
    1 行目から取る(2 か所に書くと片方だけ直したときに黙って二重取り込みになる)
  - **見出しの判定はコードフェンスの外だけ**。ルール本文にはシェルの例が入るので、
    フェンス内の `## …` を見出しと読むとそこでルールが分断される
  - **持ち出し(`export_tasks`)と取り込み(`import_tasks`)は対**。書き出したものが
    そのまま取り込みの入力になるので、テキストで手元に置けばバックアップになる。
    運ぶのは未完了タスク(タイトル・本文・状態・印)と、プロジェクトの名前・説明・
    リポジトリ(戻したいのは待ち行列であって画面の状態ではない)。**同じものを二度読んでも
    増えない**ように、(プロジェクト名, タイトル)で照合して飛ばす
  - **タスクが 1 件も無いプロジェクトも書き出す**(アーカイブしていないものだけ)。
    プロジェクトはタスクの入れ物である前に、リポジトリと説明を持つ**設定そのもの** ——
    いまタスクが無いという理由で落とすと、作り直しのたびに手で足し直すことになる。
    **アーカイブ済みで中身も無いものだけ落とす**(戻したい箱ではないため)
  - **本文は「タイトル行を除いた残り」**(`tasks.body_rest`)。メモ本体はタイトルを
    先頭に含む(検索でタイトルも引けるようにするため)ので、画面が読み書きするのは残りのほう。
    **`docs.title` は UNIQUE で、同じ 1 行目のメモがあると notes 側が `… (doc_id)` を足す**
    —— 前置きの完全一致だけで切ると、その場合にタイトル行が本文として画面に出て、
    保存でもう一度足されて二重になる

## app/views/todo.py

- `app/views/todo.py` — **ToDo の節(`section_html`)**。タスクとルールを 1 か所に出す
  サーバーレンダリングの画面で、**記憶の面のいちばん下に置く**(タスクもルールも短期記憶の
  メモにタグで載っているだけなので、面を分けると帯に同じ層の入口が 2 つ並んだ)。
  見出しは記憶の面の節と同じ段で「プロジェクトとタスク(その下に完了・書き出しと
  取り込み) → ルール」。前置きの説明と目次は置かない。
  書き込みの口は `/admin/todo/...` のままで、戻り先は記憶の面(`PAGE`)。
  使い方は `docs/tasks.md` が正。実装側の要点:
  - **プロジェクトとタスクは 1 つの表**(`_board_section`)。1 段目がプロジェクト、
    2 段目(`tr.todo-tasks`)にタスクを畳む。節を分けていた頃は、同じプロジェクトの
    説明とタスクが画面の上下に離れていた。**タスクは表にせず `div` で並べる** ——
    表の中に表を置くと、札に起こす下ごしらえ(`pages.as_cards`)が表の切れ目を
    読み違える。タスクの操作は、そのプロジェクトを開いたまま戻す(`_task_run`)。
    **タスクを足す口は行ごとのモーダル**(`_add_task_button`。`popover` 属性なので
    JS は要らない)—— 表の上に 1 つ置いていた頃は、プロジェクトを選び直す手間が
    あった。**プロジェクトを作る口は畳む**(断られたときだけ開いて戻す)
  - **外に出す面を持たない。** かつては Vue + PWA の SPA(`tasks-frontend/`)を
    別プロセス(`chiezo-tasks` / 7015)で Google のログイン付きで公開できるように
    していたが、**Chiezo は安全なネットワークの中からしか触らせない**と決めたので
    畳んだ。**守る面が 1 つでも外にあると、認証・CSRF・レート制限・リダイレクト URI の
    許可リスト・セッションの置き場を持ち続けることになる**。あわせて「画面の作りが
    2 系統ある」(サーバーで組む HTML / ビルドの要る SPA)も解消した
  - **落としたのはメモの一覧と見比べ**。前者は記憶の面とブラウズ画面で読めるし、
    後者は管理画面に同じものがある(`/admin/media`)
  - **JS はインラインの `confirm` まで**(管理画面の流儀)。開閉は `<details>`、
    並び替えはドラッグではなく ↑↓ のフォーム。**訊く文に題名を差し込むときは、
    HTML のエスケープの前に JS 側の逃がしを入れる**(`_confirm`)—— ブラウザは
    属性値の実体参照を JS に渡す前に戻すので、`'` を含む題名で文字列が途中で閉じ、
    **押しても何も起きないボタン**になる
  - **書いたら押した場所へ戻す**(303 + `#アンカー`)。**断られた理由は `?error=` で
    帯に出す**(`_run`)—— ドメイン層(`app/tasks.py`)は `HTTPException` を投げるので、
    素通しすると画面の代わりに JSON が出る
  - **✳ は Claude Code へ渡す口**(`claude_code_url`)。タイトルと本文をプリフィルし、
    プロジェクトの GitHub リポジトリと規約リポジトリをセッションに含める。
    **この層の主目的がこれ** —— 消すと、書いたタスクを人が手で貼り直すことになる。
    **タスク番号は渡さない**(向こうからこの画面を参照できないので使い道が無い)
  - **未分類のかたまりは 0 件でも出す**(放り込み先であり、プロジェクトを作る前の
    タスクが消えたように見えないため)。**手動の並び順は `app/tasks.py` が
    プロジェクト指定のときしか見ない**ので、未分類だけ `_sorted_in_group` で同じ
    2 段の並び(手で並べた順 → 作成の新しい順)に揃える
  - **入れ替えと取り込みには下見を挟む**(ルールの Markdown・タスクの JSON)。
    どちらも取り消せないので、先に何が入るかを出してから押させる

## REST

- `/v1/chiezo_memory`(POST)・`/v1/chiezo_memory/recall`(GET)・`/v1/chiezo_memory/{doc_id}`(PATCH / DELETE) —
  「覚える」層の REST。読み出しはコアスキーマなので `/v1/chiezo_memory/search|doc|filter|tags` と
  `/search/chiezo_memory/` のブラウズ画面もそのまま効く(専用の口は追記・書き換え・削除・
  時系列の想起だけ)。PATCH は渡した項目だけを差し替える(`tags` は丸ごと置き換え、
  空文字で全部外す。updated_at が現在時刻になり recall の先頭に浮く)
